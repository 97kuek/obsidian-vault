## ソケット通信
### プロセス間通信

- すべての出発点は「プロセス同士でデータをやり取りしたい」という要求
- これには2種類ある
	- 同じホスト内の2つのプロセス間通信（パイプや共有メモリなど）
	- 異なるコンピュータ上のプロセス間通信（ネットワーク越し）
- ソケット通信が扱うのは主に後者
- ただ重要なのは、ソケットという仕組みは「同じホスト内でも」「ネットワーク越しでも」同じインターフェースで書けるように設計されている点
- 相手が隣のプロセスでも地球の裏側でも、ほぼ同じコードで通信できる

### OSI参照モデルと階層化

- ネットワーク通信は複雑なので、機能を7つの層に分けて役割分担させる
- これがOSI参照モデル
- アプリケーション層（ユーザーへの機能提供）
- プレゼンテーション層（文字コードなど表現形式の吸収）
- セッション層（通信路の確立・切断）
- トランスポート層（両端ノード間のデータ転送管理）
- ネットワーク層（ネットワーク間の通信）
- データリンク層（ネットワーク内の通信）
- 物理層（ビット列を電気信号へ変換）
- **階層化のポイント**は、各層が「すぐ下の層」だけを頼りにすればよいという点
- 送信時はデータが上から下へ渡され、最終的に物理層で電気信号になってケーブルや電波で相手に届く
- 受信側は逆に下から上へ渡していく
- 各層は自分の相手（対向する同じ層）とだけ論理的に会話しているように見える、というのが設計思想
- 現実のインターネットで使われるのは、これを4層に簡略化した**TCP/IP階層モデル**

- アプリケーション層（HTTP, DNS, FTP など）→ アプリケーションプログラムが実装
- トランスポート層（TCP, UDP）→ **OS（カーネル）が実装**
- インターネット層（IP など）→ OS が実装
- ネットワークインターフェース層 → デバイスドライバとハードウェア

- つまりTCPやUDPはOSの機能であり、アプリはOSにお願いして使う、という関係
- この境界がのちの「システムコール」の話につながっていく

### カプセル化（PDUの処理）

- 各層が扱うデータの単位を**PDU (Protocol Data Unit)** と呼び、層ごとに名前が異なる
- アプリ層では「データ」
- トランスポート層では「セグメント」
- インターネット層では「データグラム」
- データリンク層では「フレーム」
- 物理層では「ビット列」
- 送信時、上の層のPDUに、その層のヘッダを付け足していく
- これが**カプセル化 (encapsulation)** 
- 荷物を送るときに、中身を箱に入れ、その箱を段ボールに入れ、段ボールに宛先ラベルを貼る…というイメージで、層を下るごとにヘッダという「ラベル」が増えていく
- 受信側では逆に、各層で自分宛のヘッダを剥がして中身を上へ渡す（**非カプセル化 / decapsulation**）

### アプリケーションの識別

- 1台のホストでは、ブラウザ・メール・SSHなど複数のアプリが同時に通信する
- IPアドレスだけでは「どのホストか」しか分からず、「そのホストのどのアプリ宛か」が区別できない
- そこで**ポート番号**を使う
	- 役割：ホスト内でアプリケーション（正確には通信の窓口）を識別する
	- 大きさ：16ビットの数値なので **0〜65,535**（2^16 = 65,536通り）
- トランスポート層のヘッダには「送信元ポート」と「宛先ポート」の両方が入る
- したがって受信側は、届いたセグメントのヘッダを見て「これはポート50000宛だからあのブラウザへ」と正しく配達できる

### ソケットとは何か

- **ソケットは、アプリケーションとネットワークの間にある通信の窓口（インターフェース）**
- アプリは、送りたいデータをソケットに「渡す」とネットワークへ流れていく
- 相手から届いたデータはソケットから「受け取る」
- 図で言うと、アプリケーションプログラムとカーネルの境界にソケットがあり、アプリはソケットの向こう側（トランスポート層以下）の複雑さを気にせず通信できる

### ソケット ≠ ポート

- ポート番号：アプリ（通信の窓口）を識別する16ビットの番号
- **ソケットアドレス：IPアドレスとポート番号の「組」**

- 例えば `192.168.1.5:12345` がソケットアドレス
- ポートだけでは「どのホストの」が抜けている
- IPアドレスとポートをセットにして初めて、インターネット全体で1つのプロセスを一意に指し示せる
- TCP通信を1本特定するには「送信元IP:ポート」と「宛先IP:ポート」の**4つ組**が必要
- したがって、同じサーバのポート80に複数のクライアントが同時接続しても、クライアント側が違えば別の通信として区別できる

### TCP と UDP

- ソケットには大きく2種類あり、これはトランスポート層のプロトコルの違いに対応する

#### TCP（ストリームソケット / 接続型）

- コネクション型
	- データを送る前に、サーバとクライアントの間で「接続」を確立する
	- この確立は後述の3-wayハンドシェイクで行う
- ストリーム型
	- データを「連続したバイトの流れ」として送る
	- 内部ではシーケンス番号を付けたセグメントに分割して送る
- 相手に確実に届き、順番も保証される

#### UDP（データグラムソケット / 非接続型）

- コネクションレス型
	- 事前の接続確立をしない
	- ハンドシェイクなし
- パケット型
	- データを個別のパケット（UDPデータグラム）の列として送る
	- シーケンス番号もない
- とりあえず投函するだけ

#### TCP vs UDP の機能差

- TCPは高信頼だが高オーバーヘッド
- UDPは低信頼（ベストエフォート）だが低オーバーヘッド
- 具体的に、TCPには次の機能が「あり」、UDPには「なし」

- 到達確認（届いたか確認する）
- 再送制御（届かなければ送り直す）
- 順序制御（バラバラに届いても正しい順に並べ直す）
- 輻輳制御（ネットワークが混んでいれば送信を控える）
- フロー制御（受信側が処理しきれない量を送りつけない）

- これらの機能があるぶんTCPは仕事が多く遅くなり、無いぶんUDPは軽くて速い、というトレードオフ

#### ヘッダサイズがそれを物語る

- TCPセグメントのヘッダ
	- **20バイト**
	- ポート番号のほかに、シーケンス番号、確認応答番号、制御フラグ、ウィンドウサイズなど、上の機能を実現するための情報が詰まっている
- UDPデータグラムのヘッダ
	- **8バイト**
	- 送信元/宛先ポート、パケット長、チェックサムだけ

#### どちらが良いか

- TCP向き
	- 信頼性が遅延より重要な場合
	- 大きなデータを確実に送りたいとき
	- 例：HTTP, FTP, SMTP
- UDP向き
	- 低遅延が信頼性より重要な場合
	- 時間にシビアな用途や、大量のクライアントからの小さな問い合わせにサーバが応える場合
	- 例：VoIP（音声通話）, DNS, SNMP, DHCP

- 音声通話は多少データが欠けても会話は続けられるが、遅れると会話にならないのでUDP、という具合

### ソケットプログラミングとシステムコール

- 同じソケットでも、立場によって見え方が違う
- カーネル視点：ソケットは通信の端点
- **アプリ視点：ソケットはネットワークへの読み書きを行うファイル記述子**
- **UNIXでは、ネットワークを含むすべての入出力デバイスをファイルとしてモデル化**する
- ソケットも「番号（ファイル記述子）」として扱われ、ファイルと同じように読み書きできる
- アプリがOSの機能を呼び出す仕組みが**システムコール**
- アプリ → システムコールインターフェース(API) → カーネル、という経路でOSにお願いする
- ソケットのAPI群（socket, bind など）は、この通信用システムコール

### ソケットのシステムコール一覧

- 主要な関数を、役割と戻り値の考え方を添えて整理する
- 共通ルールとして、成功時は0以上（多くはファイル記述子やバイト数）、**失敗時は -1** を返す

- `socket(domain, type, protocol)`
	- 通信用のソケットを1つ作る
	- `domain` はプロトコルファミリ（`AF_INET`＝IPv4など）
	- `type` は通信の種類（`SOCK_STREAM`＝TCP、`SOCK_DGRAM`＝UDP）
	- `protocol` は0で自動選択
	- 戻り値はソケットのファイル記述子
- `bind(fd, addr, addrlen)`
	- 作ったソケットに「自分のソケットアドレス（IP+ポート）」を割り当てる
	- サーバが「このポートで待ち受けます」と表明する行為
- `listen(fd, backlog)`
	- ストリームソケット（TCP）を接続待ち状態に
	- `backlog` は接続要求を溜めておくキューの最大長
- `accept(fd, cl_addr, addrlen)`
	- 来た接続要求を1つ受け付け、その接続専用の**新しいソケット**を返す
	- 元のソケットは待ち受け専用のまま残る
- `connect(fd, sv_addr, addrlen)`
	- クライアントがサーバのソケットアドレスへ接続しに行く
- `send(fd, buf, len, flags)` / `recv(...)`
	- 接続済みソケットでデータを送る/受け取る（TCP用）
- `sendto(...)` / `recvfrom(...)`
	- 接続を確立しないUDP用の送受信
	- 宛先/送信元のアドレスを毎回指定・取得する点がsend/recvと違う
- `close(fd)`
	- 通信を終了しソケットを閉じる

### アドレス構造体

- `bind` や `connect` にIPアドレスとポート番号を渡すには、決まった形の構造体に詰めて渡す
- ところがAPIは「あらゆるアドレス種別」を受け取れるように、汎用の `struct sockaddr` を引数の型にしている

```c
struct sockaddr {
    unsigned short sa_family;  /* アドレスファミリ */
    char sa_data[14];          /* アドレス情報（中身は種別による）*/
};
```

この `sa_data[14]` は「ただのバイト列」で、人間には書き込みにくい。そこでTCP/IP専用に、中身を意味のあるフィールドに分けたのが `struct sockaddr_in` です。

```c
struct in_addr {
    unsigned long s_addr;      /* IPアドレス（32ビット）*/
};
struct sockaddr_in {
    unsigned short sin_family; /* AF_INET */
    unsigned short sin_port;   /* ポート番号（16ビット）*/
    struct in_addr sin_addr;   /* IPアドレス（32ビット）*/
    char sin_zero[8];          /* 不使用（詰め物）*/
};
```

両者はメモリ上のサイズと並びが同じ（2 + 2 + 4 + 8 = 16バイト）になるよう作られています。だから実際のプログラミングでは、**書きやすい `sockaddr_in` に値を入れ、それを `(struct sockaddr *)` にキャストしてAPIに渡す**という書き方をします。APIの中では `sin_family`（=`sa_family`）を見て「これはIPv4のアドレスだな」と判断し、残りのバイトの解釈を決めます。汎用の型で受けつつ中身は柔軟に、という工夫です。

補足として、`sin_port` と `sin_addr` は**ネットワークバイトオーダー**で入れる必要があります（実務では `htons()` / `htonl()` を使う）。スライドのコード例は簡略化のため省いていますが、本来は `sin_port = htons(9734);` とするのが正しい書き方です。

### 典型的なアルゴリズム（呼び出しの順番）

- 各関数がどの順で呼ばれるかを、立場ごとに押さえてみる

#### TCPサーバ

- socket → bind → **listen** → **accept** →（recv ⇄ send を繰り返す）→ close 待ち受け用ソケットを作り、アドレスを割り当て、待ち受け状態にして、**接続が来るたびに `accept` で受け付ける**
- 処理が終わったら閉じてまた次の接続を待つ、というループ

#### TCPクライアント

- socket → **connect** →（send ⇄ recv）→ close ソケットを作って `connect` でサーバに繋ぎに行き、やり取りして閉じる
- クライアントは `bind` を明示しないことが多い（OSが自動でローカルアドレス・ポートを割り当てる）点に注目

#### UDPサーバ

- socket → bind →（recvfrom ⇄ sendto）→ close

#### UDPクライアント

- socket →（sendto ⇄ recvfrom）→ close

### 3-wayハンドシェイク

- TCPが接続を確立する仕組み
- サーバが `socket → bind → listen → accept` まで進んで `accept` で待機した状態で、クライアントが `connect` を呼ぶ
- このとき水面下で3回のやり取り（SYN → SYN/ACK → ACK）が行われ、両者が「これから通信を始めるぞ」という合意（シーケンス番号の初期値の共有など）を取りる
- 握手が成立するとクライアントの `connect` が返り、サーバの `accept` も返って、その後の `read`/`recv` へ進む
- UDPにはこの握手がないため、`sendto` でいきなりデータを投げられる

### コード例で全体を確認

スライドのコードは、クライアントが文字 'A' を送り、サーバがそれを1つ進めて（'A'→'B'）返すだけの最小サンプルです。要点だけ追います。

サーバ側の流れ:

```c
server_sockfd = socket(AF_INET, SOCK_STREAM, 0);   // TCPソケット作成
server_address.sin_family = AF_INET;
server_address.sin_addr.s_addr = inet_addr("127.0.0.1"); // ループバック
server_address.sin_port = 9734;                    // ※本来 htons(9734)
bind(server_sockfd, (struct sockaddr *)&server_address, server_len);
listen(server_sockfd, 5);                          // 待ち受け（キュー長5）
while(1) {
    client_sockfd = accept(...);                   // 接続を1つ受け付け
    read(client_sockfd, &ch, 1);                   // 1バイト読む
    ch++;                                          // 文字を1つ進める
    write(client_sockfd, &ch, 1);                  // 送り返す
    close(client_sockfd);                          // その接続を閉じる
}
```

`127.0.0.1` は**ループバックアドレス**で、自分自身との通信に限定されます（同じマシン内でサーバとクライアントを動かす実験用）。実際に外部からの接続も受けたいときは `INADDR_ANY` を使う、とスライドにも注記があります。

クライアント側:

```c
sockfd = socket(AF_INET, SOCK_STREAM, 0);
address.sin_family = AF_INET;
address.sin_addr.s_addr = inet_addr("127.0.0.1"); // サーバと同じ宛先
address.sin_port = 9734;                          // サーバと同じポート
result = connect(sockfd, (struct sockaddr *)&address, len);  // 接続
write(sockfd, &ch, 1);                            // 'A' を送る
read(sockfd, &ch, 1);                             // 返り（'B'）を受ける
printf("char from server = %c\n", ch);            // 'B' が表示される
close(sockfd);
```

サーバとクライアントで**IPアドレスとポートを一致させている**点、クライアントは `bind` せず `connect` で繋ぎに行く点を確認すると、前章のアルゴリズムがそのままコードになっているのが分かります。

## まとめ（骨格の再確認）

- ポート＝アプリの識別、ソケット（アドレス＝IP+ポート）＝プロセスの識別
- TCP（ストリーム/接続型/高信頼・高オーバーヘッド）と UDP（データグラム/非接続型/低遅延・低信頼）
- ソケットはアプリからはファイル記述子に見え、read/write できる
- システムコールの並びは「接続の有無」で理解する。TCPだけ listen/accept/connect がある
- アドレスは書きやすい `sockaddr_in` に詰めて `sockaddr` にキャストして渡す

どこか一箇所（例えば3-wayハンドシェイクの中身、`accept` が新しいソケットを返す理由、`htons` が要る理由など）をもっと深掘りしたい部分があれば、そこを重点的に説明します。
