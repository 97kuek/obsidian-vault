[Keitaro Ueki] Self-consistency/Majority voting と Best-of-N の違い
どちらも「N個の出力を生成する」ところは共通していて、*違いは選び方*にある。
Self-consistency は、複数の推論経路を生成して、それぞれから最終的な答えを取り出し、**一番多かった答え（多数決）**を選ぶ。外部の採点器は要らず、「答え同士の一致」で決める。数学の答えや選択肢問題のように、答えが離散的で「同じかどうか」を比較できるタスクに向いている。
Best-of-N は、N個生成した後に*スコアリング関数（報酬モデルやverifierなど）で採点して、一番点数の高い1個を選ぶ*。多数決ではなく、外部の評価器が良し悪しを判断する。自由記述のように「同じ答えが複数出る」とは限らないタスクでも使える。
ひとことで言うと、*多数決（答えの合意）で選ぶのが self-consistency、外部スコアラーで選ぶのが Best-of-N*。
この内容は「推論」か
そのとおり、Q1〜Q4で扱っている decoding・prompting・self-consistency・Best-of-N・Self-refine は*すべて推論時（inference-time）のテクニック*。学習済みのモデルの重みは一切変えず、「どう入力を与えるか」「どうサンプリング・選択するか」だけを工夫している。
LLMのライフサイクルの中での位置づけ
（たぶん「教科学習」は*強化学習*のことだよね）
重みを更新する*学習フェーズ*と、更新しない*推論フェーズ*で大きく分かれる。
学習フェーズ（重みが変わる）:
• *事前学習（pretraining）* — 大規模コーパスで次トークン予測を学ぶ。土台となる汎用的な言語能力を獲得する段階。
• *ファインチューニング（SFTなど）* — 指示追従や特定タスクに合わせて調整する段階。
• *強化学習（RLHF/RLAIFなど）* — 人間の選好などに合わせてアライメントする段階。
推論フェーズ（重みは変わらない）:
• *推論（inference）* — 学習済みモデルを実際に使って、プロンプトから出力を生成する段階。
今回のテクニックはこの最後の*推論*に当たる。ポイントは、prompt engineering も self-consistency も Best-of-N も*モデルの重みを触っていない*こと。学習し直すコストをかけずに、使い方の工夫だけで性能を引き出そうとしているのが、これらの手法の共通した狙いだと理解しておくといい。

第2回 キーフレーズ
:one: 大規模言語モデル（LLM）
• 大量の文章データを学習し、人間のように自然な言葉を理解・生成できる巨大なAIプログラム。
• ChatGPTやGemini、Claudeなどが代表例。
:two: 自己回帰言語モデル
• 確率の連鎖律で分解したモデルのこと。
• 「日本の、首都、は」と入力されたら、次に最も確率の高い「東京」を予測する、という連鎖で文章を作成する。
:three:デコーディング
• LLMが出力を生成するときに、次のトークン（テキストを分割した最小単位）をどのように選ぶかという方法。
:four: Greedy decoding
• デコーディングの手法の一つ。毎ステップで「一番確率が高いもの」を選ぶ方法。
:five: Top-p sampling
• デコーディングの手法の一つ。確率の高い単語から順に足していき、合計確率が指定した割合（p）に達するまでの候補の中から、サンプリングして選ぶ生成方法。
:six: プロンプティング
• 特定の機能の発生を促進 (prompt)するような言語モデルに入力するコンテキスト文。
:seven: In-context learning
• モデルの重みを更新せず、入力中の文脈や例を使ってその場でタスクを学習させること。
:eight: Few-shot prompting
•  AIに指示を出す際、少数の入出力例をプロンプトに含めて、タスクのやり方を示す方法。
:nine: Chain-of-Thought（CoT）
• 答えだけでなく、そこに至る途中の思考過程も含めて書き出すようAIに促すことで、答えの精度を上げること。
:keycap_ten: Prompt engineering
• より良い出力を得るために、プロンプトの内容や形式を設計・改善すること。
• 現在では、AI自身に最適なプロンプトを自動で作らせる研究も進んでいる。

*API スタイル選択*

*前提*

• 要求応答型・HTTP 利用可・どのスタイルも選べる状況を想定
• 例として気象データシステム（公開API／社内通信／モバイル向け）を使用
*REST（リソース中心）*

• URL でリソース、HTTP メソッドで操作
• 通常 JSON
• HTTP のキャッシュ・条件付き要求・ステータスコードをそのまま活用でき、内容も読みやすく調査が容易
• ツールが豊富で学習負担が小さく、公開 API の既定の選択肢
• 弱点：複数回の要求が必要になりがちで、過剰取得や取得不足が起きる
*gRPC（手続き呼び出し）*

• Protocol Buffers + HTTP/2
• 通信量が小さく低遅延で高性能
• 定義ファイルから多言語のコード生成ができ、型の一貫性が保てる
• 社内通信の事実上の標準
• 弱点：ブラウザから直接呼べない（gRPC-Web や Connect-RPC が必要）
• バイナリで確認しにくく公開 API 向きでない
• 両端の管理と HTTP/2 対応インフラが前提
*GraphQL（クエリ中心）*

• 単一エンドポイントにクライアントが必要なデータの形を指定
• 過剰取得・追加要求を減らせ、スキーマが契約になる
• 項目追加は既存クエリを壊さない
• 弱点：URL 単位のキャッシュ・認可・レート制限が難しい、内部クエリの分散で性能低下しうる、単純なリソース操作には過剰
*選択の基準*

• 単純さと互換性 → REST／社内の高性能・型一貫性 → gRPC／取得の柔軟性 → GraphQL
• クライアント：ブラウザ・外部開発者 → REST か GraphQL、両端を自分で管理 → gRPC
• データ：単純なリソース操作 → REST、複雑で画面ごとに形が変わる → GraphQL
*併用と結論*

• 一つに統一する必要はなく、公開＝REST／社内＝gRPC／フロントエンド＝GraphQL のような使い分けが一般的
• ゲートウェイ等で後から追加・変更も可能
• 唯一の正解はなく、クライアントと解決したい問題で選ぶ

*なぜユーザーモードとカーネルモードがあるか*
・カーネルモードでのみの特権命令
・MMUによるメモリ保護でユーザーモードプログラムはアクセスできない

*システムコール呼び出しの仕組み*
・呼び出し番号と引数をレジスタにセット
・trap 命令でカーネルモードへ切り替わり、カーネルのハンドラへディスパッチ
・処理をして、結果をレジスタに書いてユーザーモードへ復帰

*プロセススケジューリングの利点・欠点*
・FIFO:実装単純だが、短いジョブが待たされて平均応答悪化
・SJF: 平均待ち時間を最小化できるが、実行時間の事前予測必要

*抽象化と仮想化の意味*
・抽象化→複雑なハードを単純な概念に置き換えること、ディスク上のセクタ列をファイルという抽象に置き換える
・仮想化→実資源を各プロセスに占有しているように見せること、CPUを時分割して各プログラムに仮想CPUを専有している用に見せる、仮想アドレス空間
プログラマがハードの詳細他プロセスの存在を意識しなくとも、移植性、安全性高くソフトをかける

*仮装アドレス空間はなぜ必要か*
・プロセス同士の保護と隔離
・空間的局所性を用いることができる
・デマンドページングで実メモリより大きな空間が扱える

*デバイスドライバはなぜ必要か*
・標準化によりデバイスの種類に依存せず同一手続きで入出力できる

*プロセス生成時のデータ構造*
・階層化ページテーブルで使用領域に対応する下位テーブルのみを確保して削減
・fork時はCOWで親のページを共有して削減

*磁気ディスク読み出し*
・シークタイム＋回転待ち+転送時間
・最悪時間は最大シーク、一回転待ち
・ディスクソーティングSCANにより対策可能
・FIFOは到着順に処理するためヘッドが往復し、シークが増える
・シーク時間と回転待ちがボトルネックで、特にシーク時間が支配的。入力要求が複数溜まったとき、どの順で処理するかでヘッドの総移動距離が大きく変わるため、ディスクスケジューリングが必要。

*ページリプレースメントアルゴリズム*
・LRU: 最も長く参照していないページを追い出して物理メモリに空きを作る、ページフォルト率を低く抑えられる、実装が困難なのでクロックアルゴリズムなどで近似する
・FIFO: メモリに入った順で最古のページを追い出す、実装は到着順キューだけで単純だが、使用頻度を考えないためページフォルトが起きやすい

*コンテキストスイッチの役割*
・実行中の物理レジスタ内容を仮装レジスタに退避してwaitする、次に走らせる仮装レジスタを物理レジスタに復元する。終わったらwake-upする。
・これで自分専用のCPUを持つかのように中断・再開しても一貫した実行状態を保てる
・CPUの物理レジスタは1組しかないが、コンテキストスイッチ時に、実行を止めるプロセスを仮想アドレスに対比し、次に走らせるプロセスの仮想アドレスから保存値を復元する
・Ready Queueは実行可能プロセスの待ち行列（プロセススケジューリング）

forkでOS内に生成されるデータ構造
・はじめに子プロセスの仮想アドレス空間が新規に作られる。中身は親のコピーだが、新しいPIDが割り当てられる。呼び出しの戻り値は親には子のPID、子には0が返るようにようになっている。
・次にページテーブルが複製される。ただし物理メモリを丸ごとコピーするのは重いので、COWを用いる。ページテーブルのエントリは複製しつつ、物理ページは当初は読み取り専用で親子共有とし、どちらかが書き込んだときに初めてそのページだけ複製する
・最後にfd表が更新される。ディスクリプ他番号は親からコピーされる。
