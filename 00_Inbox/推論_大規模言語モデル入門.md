
## 言語モデルとは「確率モデル」

- 言語モデルは、単語列 $x_1,\dots,x_L$ に対して生成確率 $p(x_1,\dots,x_L)$ を割り当てる確率モデル
- 良いモデルとは「文法的・常識的におかしい文には低い確率を与える」もの
- 自己回帰言語モデル（Autoregressive LM）は、これを確率の連鎖律で分解する

$$p(x_1,\dots,x_L) = p(x_1),p(x_2|x_1)\cdots p(x_L|x_1,\dots,x_{L-1})$$
- **条件付き確率 $p(\text{次の単語}\mid\text{これまでの文脈})$ が分かれば「生成」ができる**
- 「日本の首都は」の次に「東京」が 0.2、「パリ」が 0.001 …という分布が出るので、そこから1語選び、また次の分布を計算する、という繰り返しになる
- さらに、翻訳・QA・要約といったタスクは全部

$$p(x_{i+1:L} \mid x_{1:i}) = \prod_{j=i+1}^{L} p(x_j \mid x_{1:j-1})$$

という「入力文脈を条件にした生成」に統一できる
- つまり **入力（プロンプト）で条件付けを変えればタスクが変わる**

## Decoding

- モデルが出すのは毎ステップの確率分布であって、文章そのものではない
- そこから実際のトークン列を作る手続きが Decoding 

### 決定的な手法

#### Greedy decoding

- 毎ステップ最大確率のトークンを選ぶ
- **局所最適 ≠ 系列全体の最適**
- 昔のモデルでは繰り返し（同じフレーズのループ）が頻発した

#### Beam search

- 候補を num_beams 個保持しながら深さ方向に探索し、系列単位のスコアで選ぶ
- Greedy の欠点は緩和されるが、計算量が beam 数倍になる
- 副作用として「当たり障りのない・短い出力」になりがち
- これは高確率系列＝ありふれた表現、かつ系列が長いほど確率の積が小さくなる（長さペナルティを入れないと短い出力が有利）ため

### 確率的な手法

**Ancestral sampling**：分布そのものからサンプリング。語彙全体（数万〜十数万トークン）が対象なので、1個1個は低確率でも裾（long tail）の合計が無視できず、時々とんでもない単語が出ます。

**Top-k sampling**：上位 k 個に絞ってサンプリング。

- 問題は **k が固定**であること。スライドの図が分かりやすくて、"The" の後は候補が広く散っている（上位k個で合計0.68にしかならない＝有望な候補を切り捨てている）のに、"The car" の後は "drives" にほぼ集中している（上位k個で0.99＝不要な低確率候補まで残している）。分布の尖り具合が文脈ごとに違うのに k が固定なのがミスマッチ。

**Top-p sampling（nucleus sampling, Holtzman et al. 2020）**：確率の高い順に足していって累積が p を超えるまでの候補集合からサンプリング。

- 候補数が文脈に応じて自動で伸縮するので Top-k より柔軟。現在の実務的なデフォルトです。

### Temperature

softmax の中に温度 $T$ を入れる：

$$p(w) = \frac{\exp(z_w/T)}{\sum_{j=1}^{V}\exp(z_j/T)}$$

- $T \to 0$：分布が尖る（実質 greedy に近づく）＝決定的・保守的
- $T$ 大：分布が平坦化＝ランダム性・多様性が上がる

ロジット $z$ を定数倍しているだけなので、順位は変わらず「差の強調度合い」だけが変わる、と理解すると早いです。

### 補足：temperature=0 でも決定的にならない

これは実務でハマる話です。原因は **浮動小数点演算の非結合性**：$(a+b)+c \neq a+(b+c)$。GPU 推論ではバッチ処理の際に、同時に来ているリクエストの数によって行列演算の分割の仕方（reduction の順序）が変わる。すると計算順序が変わり、logit の下位ビットが変わり、稀に argmax が入れ替わる。カーネル側を batch-invariant に書き直せば決定的にできる、というのが Thinking Machines の記事の主張です。

### どれを使うか

|タスク|推奨|
|---|---|
|物語生成・アイデア出し|sampling 系（多様性が価値）|
|知識質問・翻訳・分類|Greedy / Beam（正解が1つ）|

実務的には「まず greedy で1本、次に temperature や top-p を振って複数生成して見比べる」のが定石。そして「そもそも確率が高い系列＝欲しい出力なのか？」という疑問が、後半の Best-of-N（別の基準でスコア化して選ぶ）に繋がります。

## Prompting

### GPT-3 が変えたパラダイム

1. 特徴量設計 + 非NN（タスクごとにモデル）
2. アーキテクチャ設計 + NN（タスクごとにモデル）
3. Pre-train → Fine-tune（事前学習済みモデルを共有し、タスクごとに重みを更新）
4. **Pre-train → Prompt → Predict（モデルは固定、指示だけ変える）**

GPT-3 の衝撃は「**勾配更新なしで**、タスク説明と数例をテキストで与えるだけで、専用ファインチューニングに匹敵する性能が出た」こと。前兆は GPT-2 にもあって、質問の後に "A:" と書くと答えるとか、"TL;DR:" と書くと要約が出る、といった現象が観測されていました。

### In-context Learning

- 重みを固定した LM が、プロンプト内の例示による条件付けだけでタスクを実行すること

- **Zero-shot**：タスク説明のみ（"Translate English to French: cheese =>"）
- **One-shot**：例が1つ
- **Few-shot**：例を複数（"sea otter => loutre de mer" などを並べてから本題）

- **例示数を増やすと性能が上がる**
- 特にモデルが大きいほど効く
- さらに long context 時代になり、Many-Shot ICL（Agarwal et al. 2024）では 500-shot、8192-shot といった規模で大幅改善が報告されている
- ただしコンテキストが伸びれば計算量とコストが増えるので、そこから先は Fine-tuning の話になる

### Chain-of-Thought（CoT）

- 多段階推論が必要な問題（算数の文章題など）では、いきなり答えを出させると間違える
- そこで **答えに至る途中の思考過程を書かせる**

- **Few-shot CoT**
	- 例示の中に推論過程を含める
	- 「ロジャーは5個持っていて、3個入りの缶が2つだから6個、5+6=11」
	- モデルサイズが大きいときに改善幅が大きい（創発的）
- **Zero-shot CoT**
	- 例示すら与えず、"**Let's think step by step**" と付けるだけ
	- 「パイプラインを人間が設計するよりモデル自身に考えさせた方がいいのでは」という発想から生まれたフレーズ


- 多段階推論では、大幅改善
- シングルステップで解ける常識推論では→ **むしろ下がる**ことがある。考えすぎて、ありえる選択肢を複数拾ってしまう。

#### なぜCoTが効くのか

- Transformer は固定深さの並列計算モデル
- 本質的に逐次的な問題を1回の forward では解けないが、中間トークンを出力すること＝計算ステップを時間方向に伸ばすことで表現力が上がる
- **思考トークンは装飾ではなく、計算資源**

### プロンプトの脆さ


- 同じタスクでも聞き方で精度 40.9% → 71.2%
- 区切り文字やスペース、大文字小文字を変えるだけで 0.036 〜 0.804 という幅
- Zero-shot CoT のトリガー文も "Let's think step by step" 78.7 に対し "Let's think" 57.5、無関係な文（"Abrakadabra!"）15.5
- **プロンプトの微差で性能が動く以上、評価セットを持たずに「良くなった気がする」で判断してはいけない**

### プロンプト自動最適化

人手の試行錯誤を自動化する系譜：

- **APE（Zhou et al. 2023）**：入出力ペアから指示文を LLM に複数生成させ、スコア（タスク性能や尤度）で選択、さらに言い換えで候補を増やす。生成された "Let's work this out in a step by step way to be sure we have the right answer." が人間製を上回った（82.0）。
- **DSP（Demonstrate-Search-Predict, Khattab et al. 2022）**：質問分解や follow-up 質問といった中間過程を LLM の試行錯誤で作り、最終出力が正解と一致したかで中間過程の良し悪しを判定する。※スライド40の出典表記は APE のものと取り違えているようです（正しくは "Demonstrate-Search-Predict"）。
- **OPRO（Yang et al. 2024）**：過去のプロンプトとスコアの履歴をメタプロンプトに入れて「もっとスコアが高くなるプロンプトを作れ」と LLM に指示。LLM を最適化器として使う。
- **GEPA（Agrawal et al. 2025）**：実行の成功・失敗の軌跡から**言語フィードバック**を作ってプロンプトを改善。加えて Pareto フィルタリング（1問だけでも最高スコアを出したプロンプトも候補に残す）で多様性を確保。RL（GRPO）より遥かに少ないロールアウト数で上回る、というのが売り。スライド43の Before/After は「1行のシード」が「構造化された数十行の指示書」に育つ様子で、これは DSPy 系のツールで実際に使えます。


## Meta-generation

- Decoding が「1回の生成の中の話」なのに対し、Meta-generation は「モデルを複数回呼んで最終出力を得る」レイヤー
- Welleck et al. 2024 は以下の3パターンに整理
	- **(a) Parallel search**：並列に生成して集約
	- **(b) Heuristic step-level search**：ステップごとに生成→選択→追加
	- **(c) Refinement**：生成→フィードバック→修正のループ

### 具体手法

#### Self-Consistency（多数決）

- sampling で複数の CoT を生成し、最終答えの多数決を取る
- 推論経路は違っても正解は一致しやすい、という仮定
- 検証器不要で実装が簡単なのが強み（ただし答えが離散的なタスク限定）

#### Best-of-N

- N 個生成してスコア化し、最高スコアを選ぶ。多数決と違い、**スコア関数**が必要

**スコアの付け方**

1. 専用の分類器を学習：Reward Model / Process Reward Model（最終結果だけでなく途中ステップを評価）
2. **LLM-as-a-Judge**：LLM にプロンプトで評価させる。「公平な審判として振る舞い、helpfulness/relevance/accuracy/depth などを考慮し、位置バイアスを避け、[[A]]/[[B]]/[[C]] の形式で出力せよ」というプロンプト。人間の評価とそれなりに一致するが、**長い回答を高く評価しがち**などのバイアスがある（他にも位置バイアス、自己生成物優遇バイアスなど）。評価観点を細かく指定すると改善する。

#### SELF-REFINE

- 同じモデルに、生成 → 自分の出力へのフィードバック → 修正、をプロンプトを変えて回させる
- ただし **外部からの正解情報なしの自己修正は必ずしも改善しない**ので、テストの実行結果やコンパイルエラーのような外部フィードバックと組み合わせるのが実務的

## 発展的なプロンプト例

### システムプロンプト

- Claude では 2500 words 規模
- 属性情報（名前・プロダクト情報、retrieve して使う）、ジャンルごとの応答姿勢、フォーマット指定、knowledge cut-off、米大統領選の結果などが入っている

#### 敵対的プロンプト

- DAN のようなジェイルブレイク
- 加えると攻撃成功率が上がる敵対的サフィックスの存在も知られている

- 慶應大が授業資料に透明色の文字で「別趣旨のレポートを書け」と仕込む、論文に「高評価せよ」を隠す（日韓米14大学）
- **モデルは「データ」と「命令」を区別しない**という根本的脆弱性の表れで、RAG やエージェントを作る側からすると最重要の脅威モデル

#### DeepResearch のプロンプティング実装

- クエリ生成 → 検索 → 十分かの reflection → 足りなければ追加検索 → 回答生成、というループ

#### Paper2Poster

- LLM 単体でなく、図の切り抜き処理や python-pptx などのライブラリと組み合わせ

#### 合成データ

- TinyStories / Physics of LM（統制実験用）、WizardLM / Alpaca（複雑化・自己教示）、s1K / NaturalThoughts（大モデル→小モデルの蒸留）、Textbooks Are All You Need（高品質事前学習データ）。Alpaca は 175 シードタスク → text-davinci-003 で 52K 命令データ → LLaMA 7B を SFT、という流れ

#### シミュレーション

- 2時間のインタビュー記録をエージェントの記憶として与え、1000人分の人間の回答を模擬

### Context Engineering

- 次の手順・処理のために、コンテキストウィンドウを最適な情報で満たす、繊細なアートであり科学」
- プロンプトに加えて、RAG・Tool-use、状態管理・マルチモーダルが含まれるGemini Plays Pokémon のアーキテクチャ図が具体例で、永続メモリ、目標の階層（Primary/Secondary/Tertiary）、行動履歴の要約、専用ツール（Pathfinder など）と、コンテキストをどう構成するかの設計そのものになっています。

## モデルの選択

### アクセス手段

| 種類     | 特徴                         | 例                                       |
| ------ | -------------------------- | --------------------------------------- |
| API のみ | 重み非公開、従量課金、GPU 不要          | GPT, Gemini, Claude                     |
| 公開モデル  | 重み公開、手元で動く、データを外に出さない、分析可能 | Llama, Mistral, DeepSeek, Qwen, gpt-oss |
| 非公開モデル | 一部研究機関のみ                   | PaLM, Gopher                            |

- 「公開モデル」は "open-weight" であって、学習データやコードまで公開の "open-source" とは限らない点に注意
- **ライブラリ**：Transformers（HuggingFace＝モデル・データセット版 GitHub、ただしバグ混入もあるので不具合時はバージョン確認）、vLLM（高速推論）
- **計算資源**：自前 GPU（H100 80GB 約600万円＋電力＋保守＋環境構築）／クラウド GPU（H100 $1.49/h 程度も）／ホスティングサービス（Cerebras, Groq, Together.ai, Fireworks — 独自の高速化・軽量化技術を持ち、速度と価格でトレードオフ）

### 性能の見方と落とし穴

- **リーダーボード**：lmarena（ユーザー投票型・Elo）、HELM（複数ベンチ総合）、日本語なら Nejumi LLM リーダーボード4（汎用的言語性能 GLP とアラインメント ALT の2軸）。
- **自前評価ツール**：simple-evals（OpenAI）、llm-jp-eval、Lighteval。
- **注意点（重要）**：
    - プロンプトの書き方や選択肢の絞り方で、**同じモデル・同じベンチマークでもスコアが大きく変わる**（HuggingFace の Open LLM Leaderboard MMLU 問題）。
    - **同じモデルでもホスティング先の設定で性能が変わる**（gpt-oss-120b の GPQA が提供元により 72.7%〜79.0%）。量子化やデコード設定の違いによるもの。
    - リーダーボード自体の構造的バイアス（The Leaderboard Illusion）。

### 実務的な指針

- とりあえず**一番性能の良いモデル**から試す
- 無料版で判断しない
- 安いモデルへの最適化は、まず高いモデルで動くことを確認してから
- **OpenRouter** で同一インターフェースから複数モデルを横並び比較。スライドの「東京のアツアツ・キンキン・ガラガラのサウナ」の例は、Gemini 2.5 Pro / Claude Sonnet 4 / Grok 4 / GPT-5 が**全部不正解**（正解はオールドルーキーサウナ）という、ローカルでニッチな知識の限界を示す例です。→ こういう知識は RAG で外から入れるべき、という含意。
