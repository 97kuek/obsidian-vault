## オペレーティングシステムA：データ構造と計算機システム

## 導入

- OS のカーネルは、結局のところ **C言語で書かれた、ポインタとキューとハッシュだらけのプログラム**
- プロセスを待たせる → **キュー**
- プロセス ID からプロセス構造体を引く → **ハッシュ表**
- 構造体を数珠つなぎにする → **ポインタと連結リスト**
## 計算機システムの構成

![[計算機システムの構成.png]]

| 要素                 | 役割                        | OSとの関係                     |
| ------------------ | ------------------------- | -------------------------- |
| **CPU<br>レジスタ**    | 演算の実行主体                   | コンテキストスイッチ時にレジスタを退避・復元     |
| **PC**             | 次に実行する命令のアドレス             | ここを書き換える＝実行の流れを変える         |
| **SP**             | スタックの先頭アドレス               | 関数呼び出し・プロセス切り替えの要          |
| **キャッシュメモリ**       | 低速なメモリを補う高速小容量メモリ         | プロセスを切り替えるとキャッシュが無効になり遅くなる |
| **MMU**            | **仮想アドレス → 物理アドレス**の変換と保護 | 仮想記憶・プロセス間の分離を実現する心臓部      |
| **バス<br>バスコントローラ** | CPU・メモリ・I/O をつなぐ通り道       | 帯域がボトルネック                  |
| **I/Oデバイス**        | 外部との入出力                   | デバイスドライバが担当                |

## プログラムができるまで

### コンパイル

- 高級言語（C, C++）→ **コンパイラ** → マシン語

### リンケージ

- `read(fd, buf, BUF_SIZE)` と書いても、`read` の中身は自分のソースにはない
- **リンカ**がライブラリのオブジェクトファイルをくっつけて、1つの実行ファイルにする

- **静的リンク**：実行ファイルにライブラリを埋め込む。ファイルは大きいが単体で動く。
- **動的リンク**：実行時に共有ライブラリ（.so / .dll）を読む。メモリを共有でき、更新も楽。これを実行時にやるのは**OS のローダ**の仕事。

## プログラムの実行

### 命令の4分類

|種類|例|説明|
|---|---|---|
|メモリ転送|`move 10000 r1`|メモリ↔レジスタ|
|算術|`add r1 100`|**レジスタ同士**の演算|
|条件分岐|`Cjmp r2 2000`|r2 が 0 なら 2000番地へ|
|関数呼び出し|`call 3000`|戻りアドレスを積んでジャンプ|

### 名前の解決

```c
int error;          /* 大域変数 */
func2(){ error = 10; }
```

- CPU は `error` という名前を知らない
- コンパイラが**シンボルテーブル**で `error → 10000番地` と対応づけ、`move 10000 #10`（10000番地に 10 を書け）という命令に変換する
- **名前 → アドレスへの変換**が「名前の解決」

### 場所の解決

- `call read` も同じで、`read` が何番地にあるかはコンパイル時点では不明
- だから一旦 `call 0` にしておき、**リンク時に `call 5000` へ埋め直す**
- これを**再配置**と呼ぶ

### スタックとローカル変数

- **ローカル変数はスタック上に確保される** 
	- 関数を呼ぶたびに新しい領域が積まれ、抜けると自動的に捨てられる → 有効範囲が関数内に限られる
	- **再帰呼び出しができる**のもこのおかげ（呼び出しごとに別の `i, j` を持てる）

### プロセスのメモリレイアウト

| 領域            | 中身                      | 特徴                  |
| ------------- | ----------------------- | ------------------- |
| **コード（テキスト）** | 機械語命令                   | 読み取り専用・実行可          |
| **データ**       | 大域変数 `static int a, b;` | プログラム開始から終了までずっと存在  |
| **スタック**      | ローカル変数・戻りアドレス           | 関数の出入りで伸縮、**下に伸びる** |

## プログラムの起動

![[プログラム起動とプログラムカウンタ.png]]

1. OS が実行ファイルを読み、コード・データを**メモリ上に配置**する
2. スタック領域を用意し、SP を設定する
3. **プログラムカウンタに開始番地（例：4096）を代入する** ← これで実行が始まる

## OSの起動

1. 電源投入（Power On）... 電源が安定すると Power Good 信号が出て、CPU がリセット解除される。
2. ファームウェア起動 & POST ... **UEFI / BIOS** が起動し、**POST（Power On Self Test）** でメモリや基本デバイスを自己診断・初期化する
3. ブートデバイス検索 ...  どこから OS を読むかを決める（SSD → USB → ネットワーク の優先順）
4. ブートローダのロード ... GRUB や Windows Boot Manager を ESP からメモリに読み込んで実行
5. OSカーネルの起動 & 実行 

## アーキテクチャ用語

| 用語                    | 内容                                           | OSとの関係                                            |
| --------------------- | -------------------------------------------- | ------------------------------------------------- |
| **多段キャッシュ（L1/L2/L3）** | CPU に近いほど小さく速い                               | コンテキストスイッチでキャッシュが汚れる → **CPUアフィニティ**（同じコアで動かす）が効く |
| **パイプライン処理**          | 命令を fetch/decode/execute の段に分け、複数命令を重ねて流す    | 分岐や割り込みでパイプラインが**フラッシュ**され性能が落ちる                  |
| **スーパスカラ**            | 実行ユニットを複数持ち、独立な命令を**同時に**実行                  | IPC（1サイクルあたりの命令数）が1を超える                           |
| **Out-of-Order 実行**   | 依存関係のない命令を順番を入れ替えて先に実行                       | **Spectre / Meltdown** の温床。投機実行の痕跡がキャッシュに残り情報が漏れる |
| **SIMD（GPGPU）**       | 1命令で複数データを同時処理                               | レジスタが巨大なのでコンテキストスイッチの退避コストが増える                    |
| **VLIW**              | 同時実行可能な複数命令を1つの長い命令に詰める。並列化の判断を**コンパイラ**に任せる | ハードは単純化できるがコンパイラが複雑化                              |

- Out-of-Order = **実行時にハードウェアが**見つける
- VLIW = **コンパイル時にソフトウェアが**見つける
- SIMD = **データ側に**並列性を見つける
