## トランスポート層

- **異なる端末上のプロセス間通信を提供する層**
- TCPのように信頼性を提供する方式も、UDPのように最小限のデータグラム転送だけを提供する方式もある
### 概要

#### 役割

- 下の層（インターネット層 ）は **コネクションレス** で、パケットが届く保証も順番の保証もない
- トランスポート層は、その上に乗って **効率的かつ信頼性のあるデータ転送サービスを上位層（アプリ）に提供**する
#### 抽象化

- **アプリ開発者が下位層の違いを気にしなくてよくなる** こと
	- ネットワークインタフェースの違い（有線/無線など）を意識しなくてよい
	- 信頼性のレベルの差を意識しなくてよい
	- 開発者は `socket()`, `bind()`, `listen()`, `accept()`, `send()`, `recv()`, `close()` といった **ソケットAPI** を呼ぶだけでよい
- ソケットAPIとシステムコールとしての見え方は [[04_ソケット通信]] に整理している

#### 主要なトランスポート層プロトコル

| 略称(番号)       | 正式名称                                 | 通信方式     | 特徴                                   |
| ------------ | ------------------------------------ | -------- | ------------------------------------ |
| **TCP** (6)  | Transmission Control Protocol        | コネクション指向 | 最もよく使われる。確実かつ効率的な転送                  |
| **UDP** (17) | User Datagram Protocol               | コネクションレス | 最小限の機能。リアルタイム用途                      |
| **QUIC**     | QUIC                                 | コネクション指向 | UDP上で動作する、暗号化・多重化されたIETF標準トランスポート |
| SCTP (132)   | Stream Control Transmission Protocol | 両方       | マルチホーム（冗長経路）対応の高機能版                  |
| DCCP (33)    | Datagram Congestion Control Protocol | コネクション指向 | 輻輳制御に機能を絞る。信頼性なし                     |
### TCP が提供する4つの機能

| 機能            | 目的      | 内容のひとことまとめ                 |
| ------------- | ------- | -------------------------- |
| **コネクション管理**  | 高信頼     | コネクションの確立・維持・解放の手順         |
| **フロー制御**     | 高効率＋高信頼 | スライディングウィンドウ。受信側の処理能力に合わせる |
| **タイムアウト/再送** | 高効率＋高信頼 | ロスしたら適切なタイミングで再送           |
| **輻輳制御**      | 高効率＋高信頼 | ネットワークの混雑を起こさないようウィンドウ調整   |

#### データリンク層で再送しているのに、なぜトランスポート層でも再送？

- 802.11（Wi-Fi）などデータリンク層でも再送はしている
- それなのにトランスポート層でも再送が必要な理由は、**動作する対象・距離・エラーの種類が違うから** 

| レイヤ      | 典型的な距離               | 時間スケール   | 通信対象                       | 再送の原因となるエラー |
| -------- | -------------------- | -------- | -------------------------- | ----------- |
| データリンク層  | **単一リンク**            | リンクごとの遅延 | 無線干渉、リンク上のフレーム損失など         |             |
| トランスポート層 | **複数リンクで構成されるE2Eパス** | 経路全体のRTT | 各リンクの損失、ルータのバッファあふれ、経路変化など |             |

- データリンク層は「隣の機器との1ホップ」しか面倒を見ない
- E2Eの経路全体で起きるパケットロスは、各リンクのデータリンク層では検知できない
- したがってアプリケーションが経路全体の信頼性を必要とする場合、TCPやQUICなどエンド端末側の仕組みで補う必要がある（**エンドツーエンド原理**）

### TCPの動作メカニズム

#### TCPのゴール

- **高信頼性 ＝ データの整合性**
    - データを順番どおりに上位層へ届ける
    - パケットロスを回復する
    - 輻輳崩壊を避ける
- **高効率 ＝ 転送レートを上げる**
    - スライディングウィンドウのサイズを動的に調整し、状況に最適なレートで送る

![[Pasted image 20260720155754.png]]

### コネクション管理

#### コネクション指向とは

- 2台の端末が通信を始める前に **コネクションを確立**
	- TCPコネクションとアプリケーションのセッションは対応する場合もあるが、同義ではない。1セッションが複数コネクションを使うこともある
	- セッションは **5-tuple** で一意に決まる
		- ① 発信元IPアドレス
		- ② 宛先IPアドレス
		- ③ プロトコル番号(TCP)
		- ④ 発信元ポート番号
		- ⑤ 宛先ポート番号

#### ポート番号

- 上位層のアプリケーションを指定する識別子
    - 80: HTTP、443: HTTPS、25: SMTP、8333: bitcoin など
- ポート番号により **通信の多重化** が可能
	- 2端末間で複数のTCPセッションを同時に張れる（並列化）

#### TCP状態遷移ダイアグラム

**クライアント側**

- 最初は`CLOSED`で何もしていない状態
- アプリが接続したいと`active open`になると、`SYN`を送って**SYN_SENT**
- 相手から`SYN・ACK`が返ってきたら、こちらが`ACK`を送って3-wayハンドシェーク完了
- **ESTABLISHED**になる
- 通信が終わって`active close`になると、`FIN`を送って`FIN_WAIT_1`へ
- **自分の`FIN`への`ACK`が返るとFIN_WAIT_2**
- 相手の`FIN`が届いたら`ACK`を返して`TIME_WAIT`へ


![[Pasted image 20260720160018.png]]


**サーバ側**

- `passive open`で**LISTEN**に入る。これはサーバ特有の状態
- クライアントから`SYN`が来たら`SYN・ACK`を返して`SYN_RCVD`．続いて`ACK`を受け取れば3-wayハンドシェーク完了で`ESTABLISHED`
- 切断はクライアントから`FIN`が来るので、`ACK`を返して**CLOSE_WAIT**へ
- 自分のアプリが閉じる準備が出来たら`FIN`を送って**LAST_ACK**へ

![[Pasted image 20260720160205.png]]

#### コネクションのリセット（RST）

- サービスを提供していないポートへの接続要求を受けたとき
- FINの代わりにRSTで終了させるとき（プログラムが途中で落ちた等）
- **RSTを受信した場合、ACKは不要**（普通の終了と違う点）

### フロー制御

#### スライディングウィンドウ

- 逐次応答だと、遠距離通信では待ち時間が長く非効率
- そこで **ウィンドウサイズの範囲内で複数のセグメントをまとめて送れる** ようにする
- TCP は高遅延環境が多いのでこの方式を採用
- 整合性のために2つの番号を使用する
	1. **Seq**：送るデータを **バイト単位** で区切った位置番号
	2. **ACK**：受信側が「**次に受け取るべき**シーケンス番号」を送信側へ通知する値

![[Pasted image 20260720160410.png]]

#### 受信側からのフィードバック

- **受信側の処理能力に送信量を合わせる** のがフロー制御
	- 受信ホストが「いま受信可能なデータサイズ（広告ウィンドウ）を明示的に通知する
	- TCPヘッダの **ウィンドウサイズフィールド** を使う
	- **win=0 を返したら、送信側はセグメントを送ってはいけない**
	- 待機中、送信側は定期的に **ウィンドウプローブ** を送って受信側の状況を確認する
	- 受信側が回復したら新しいwin値を返す

![[Pasted image 20260720160457.png]]

#### フロー制御と輻輳制御の違い

- **フロー制御** … **受信側の処理能力**に合わせる（相手があふれないように）
- **輻輳制御** … **ネットワーク全体の混雑**に合わせる（経路があふれないように）
- ウィンドウサイズはこの両方を考慮して決める
- 実際の送信可能量は **min(広告ウィンドウ, 輻輳ウィンドウ)** 

#### タイムアウト/再送

#### 再送タイミングの決め方が難しい理由

- **早すぎる** → まだ確認応答が届いていないだけなのに再送してしまい、行き違いが起こる
- **遅すぎる** → ロスに気づくのが遅れて転送効率が落ちる
- 適切なタイミングは **RTTに依存** する
- しかも **RTTは変動する**→再送タイマーRTO

#### 再送タイマーRTO

- 送信側は再送タイマーを持ち、時間切れになったら再送する
- RTOは**計測したRTTの変動を使って動的に計算**する

##### 移動平均をとることによる平滑化

![[Pasted image 20260720160843.png]]

- `SRTT` … 平滑化したRTT（指数重み付き移動平均）
- `RTT` … 今回計測した実測RTT


##### 平均偏差を使ってRTOを決める

- 本来は標準偏差を使いたいが計算が重いので、**平均偏差**で代用する

![[Pasted image 20260720160826.png]]

#### Karnのアルゴリズム

- 再送が絡むと**届いたACKが、最初の送信に対するものか再送に対するものか分からない**
- これに対処するのがKarnのアルゴリズム
	1. **再送したセグメントの計測値はRTT計算に使わない**
	2. 再送しても応答がなければ、**RTOを2倍にする**
	3. 失敗が続けばさらに2倍…（**指数バックオフ**）

### 輻輳制御

#### ネットワークの輻輳と「輻輳崩壊」

1. 多数の送信元が高速にデータ転送
2. 帯域幅を超える通信要求
3. ルータが過負荷
4. パケットロス発生
5. 各端末がさらに再送を要求
6. 通信要求がさらに増大
7. すべての端末が通信不能（＝輻輳崩壊）

#### 輻輳崩壊を避けるには
##### 暗闇のキャッチボール

- 各端末がネットワークの混雑状態を**推定しながら**ウィンドウサイズを調節
- 混雑の信号には、パケット損失、RTT増加、ECNによる明示通知など
- TCPの重複ACKやタイムアウトは再送要求そのものではなく、送信側が損失を推定する材料

##### 輻輳ウィンドウ（cwnd）と AIMD

- 輻輳ウィンドウ を導入
- 送信側は cwnd を超えるパケットを送れない
- cwnd は AIMD で制御
    - **加算増加**：問題なければ少しずつ増やす（慎重に攻める）
    - **乗算減少**：ロスが起きたら一気に減らす（半分など。素早く退く）

**スロースタート**

![[Pasted image 20260720162014.png]]

- **スローは初期値が小さいことを指す**（増え方は実は速い＝指数的）
- cwnd が **スロースタートしきい値** より小さく、輻輳が検出されない間は継続する

**輻輳回避（cwnd > ssthresh になったら）**

![[Pasted image 20260720162128.png]]

**高速再送**

- タイムアウトを待つのは時間の無駄なので、**ロスをいち早く検知** する仕組み
- ロスが起きると、受信側は **同じ確認応答番号のACKを繰り返し送る**（「次は1001以降」を何度も）
- 送信側は **3つの重複ACK** を受けたら、そのセグメントがロスしたと判断して**即座に再送**

![[Pasted image 20260720162214.png]]

**高速回復**

- 再送のたびに cwnd を1に戻すのは非効率
- そこで **高速再送だった場合は次のようにする**
	- ssthresh を **再送直前の cwnd の半分** に設定
- ACK処理中の一時的なcwnd膨張を経て、回復完了後はssthresh付近から輻輳回避を続ける
	- ただし **高速再送できないロス** の場合は、cwnd を1に戻して**スロースタートからやり直し**

#### TCP Tahoe と TCP Reno の違い

|           | ロス検知時の動作                                            |
| --------- | --------------------------------------------------- |
| TCP Tahoe | ロス時はcwnd=1に戻してスロースタートからやり直し                         |
| TCP Reno  | TCP Reno = TCP Tahoe + 高速回復。重複ACKのときはcwnd半減+輻輳回避で再開 |

## TCP/UDPのヘッダ構造

### TCPヘッダの構造

![[Pasted image 20260720162528.png]]

#### フラグの意味

|フラグ|意味|
|---|---|
|NS, CWR, ECE|ECN（明示的輻輳通知）用|
|URG|緊急データの有無|
|ACK|確認応答番号が有効。確立後の多くのセグメントで1になる|
|PSH|受信側へ、バッファしたデータをアプリケーションへ速やかに渡すよう促す|
|RST|1ならコネクションを強制切断|
|SYN|1ならコネクション確立要求|
|FIN|1ならコネクション切断要求|

#### ポート番号の使い分け

- **クライアント側の発信元ポート**：OSが利用可能な範囲からエフェメラルポートを動的に選ぶ。IANAのDynamic/Private範囲は49152〜65535だが、実際のOSの選択範囲は異なる場合がある
- **サーバ側の発信元ポート**：well-knownポート（0〜1023）や登録済みポートを使う（IANA管理）

#### ウィンドウサイズと最大スループット

- 16bit なので **最大65535バイト**
- もっと大きくしたい場合は、3-wayハンドシェーク時にオプションで **ウィンドウスケーリング** を指定：`ウィンドウサイズ × 2^s`（s=0〜14）→ 最大 65535×2^14 ≈ **約1GB**
- **TCPの最大スループット理論値**：

```
スループット = W / RTT      （W: ウィンドウサイズ）
```


### UDPヘッダの構造

![[Pasted image 20260720162604.png]]

- ヘッダ長は **常に8バイト**
- UDPチェックサムはIPv4では0として省略可能だが、IPv6では原則必須である

#### UDPの特徴

- コネクションレス通信、ヘッダのオーバーヘッドが少ない
- **信頼性・順序性は保証されない**（コネクション管理・輻輳制御・シーケンス番号管理・再送が**すべてない**）
- チェックサムのみ提供
- **UDP-Lite**：チェックサムエラーでも全廃棄せず、計算範囲をアプリが指定。エラーがあってもデータを渡す（リアルタイム映像・音声向け）

## QUIC

### なぜ新しいトランスポート層プロトコルが必要になったか

- TCPが生まれた80年代から環境が大きく変化
	- **クラウド通信の普及** → 遠いホストとの通信が増えた（遅延が高い）
	- **無線ネットワークの普及**
	- **Webが通信の中心に** → 100msの差が大きな収益差につながる
	- **通信の暗号化が必須に**

### 上位層の対応では不十分な理由

- HTTP/2 は多重化で **HTTP HOLブロッキング** を解決した
- しかし **トランスポート層で起きる TCP HOLブロッキング** は解決できない
- **ハンドシェーク起因のオーバーヘッド（TCP＋TLSで複数RTT）** も上位層では解決不能

### QUICとは

- Googleの実験的プロトコルを起点にIETFで再設計・標準化された。IETF QUICでは「QUIC」を正式名称として扱う
- 実現する機能
    - **コネクション確立時間の短縮**
    - 輻輳制御の改善
    - **HOLブロッキング対策**
    - **トランスポート層での暗号化＋認証**された通信

### なぜ UDP の上に作るのか

| 理由     | 説明                                                                                       |
| ------ | ---------------------------------------------------------------------------------------- |
| 実装コスト  | 新プロトコルはOSに採用されないと普及しない<br>良い技術でも採用されるとは限らない<br>**UDPなら実績があり、OS改修不要ですぐ使える**               |
| NAT/FW | UDPは既存機器で扱える一方、UDPを遮断するネットワークや短いNATタイムアウトもある<br>QUICが常に通過できるわけではなく、実装はTCPへフォールバックする場合がある |
| 軽量さ    | UDPはオーバーヘッドが少ない                                                                          |
| 自由度    | 既存TCPに依存せず1から開発できる                                                                       |
