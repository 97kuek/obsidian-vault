## 情報通信ネットワークA：文字コードとWeb技術

- 親ノート: [[情報通信ネットワークA]]

## 文字コード技術

### 文字コードとは

#### 符号化という考え方

- 文字コードとは、**コンピュータで文字を処理するために、文字に番号を割り当てる規則・規格**
- 文字コードが表すのは図形情報ではなく、**文字を抽象化した情報**
- 「あ」という文字の"概念"に番号を振っているのであって、フォントの見た目とは別物
- 符号化とは、文字を {0, 1} のビット列で表現すること

#### 文字集合 vs 符号化文字集合

|用語|英語|意味|
|---|---|---|
|**文字集合**|character set|システムで扱う文字の"集まり"。番号はまだ振っていない|
|**符号化文字集合**|coded character set|文字集合を定義し、**各文字にコード（ビット組合せ）を割り当てた**もの|

- 各コードポイントを示す表を**コードチャート**と呼ぶ
- 見た目が同じ文字列でも、合成済み文字と結合文字列のように複数のコードポイント列で表せる場合がある
- 比較時にはUnicode正規化が必要になることがある
- UnicodeとISO/IEC 10646は別組織が保守する規格だが、コードポイントの割り当ては同期されている

#### 符号化文字集合 vs 文字符号化方式

| 用語          | 意味                                      |
| ----------- | --------------------------------------- |
| **符号化文字集合** | コードを割り当てた文字の集合そのもの                      |
| **文字符号化方式** | コードポイントや符号位置を、保存・通信に使うコード単位やバイト列へ変換する方法 |

#### ASCII (ISO/IEC 646)

- 最初に標準化された符号化文字集合
- **ASCII** = American Standard Code for Information Interchange
- ANSI が策定、**1963年初版**
- **7ビット**（128文字）
- 国際標準化したのが **ISO/IEC 646**（各国版が定義）

#### なぜ7ビットだったのか

- 当時は**データリンク層のコストが高く**、なるべく少ないビットで送りたかった
- 1バイト=8ビットのうち**最上位ビットをパリティチェック**（誤り検出）に使っていた
- バイナリは uuencode 等でいったん ASCII(7ビット) に変換して送信

### 制御文字と図形文字

- **図形文字**：画面に表示できる普通の文字
- **制御文字**：改行など出力を制御する特殊コード

#### 内部コードと外部コード

- **内部コード**＝システム内部の処理用
- **外部コード**＝入出力用
- 現代の主要OSや言語処理系はUnicodeを扱うが、内部表現はUTF-8、UTF-16、UTF-32や独自表現など実装によって異なる
- ファイルやWebではUTF-8が広く使われる

#### 文字コードの変遷

| 段階         | 時期      | 内容             |
| ---------- | ------- | -------------- |
| ASCIIと各国対応 | 1960年代～ | アメリカで誕生 → 他国へ  |
| 複数バイト文字集合  | 1970年代～ | アジアの文字（漢字）への対応 |
| 国際符号化文字集合  | 1990年代～ | 世界で統一された文字へ    |

### 代表的な符号化文字集合と符号化方式

#### ASCII → 各国言語への対応

- ASCIIは英語向けなので各国が**各国版ISO/IEC 646**を作成
- 一部を自国文字に置き換えたため後に互換性問題を起こす

#### 複数バイト文字集合と ISO/IEC 2022

- 漢字は1バイト（256通り）では足らず**2バイト文字**を提案
- 各国版切替や多言語同時表示を解決する**符号化方式**が **ISO/IEC 2022**
- インターネット想定で当初は**7ビット符号**
- **エスケープシーケンス（ESC=0x1B）で文字集合を切り替える**のが核心

#### Unicode と ISO/IEC 10646

- 文字集合を切り替えるのではなく、**1つの大きな表に全文字を入れる**発想
- 同時期に2規格が並行

|                | ISO/IEC 10646 | Unicode   |
| -------------- | ------------- | --------- |
| 立場             | 国際標準          | 民間コンソーシアム |
| 初期コード帳         | 4バイト          | 2バイト      |
| ISO/IEC 2022互換 | あり            | なし        |

- 最終的に **ISO/IEC 10646 を Unicode に合わせる**形で妥協し同一コード表に
- このとき日中韓台の漢字を統合（**CJK統合漢字**）→ JIS X 0208資産がそのまま使えない・字形差などの問題
- **BMP**はU+0000–U+FFFFの範囲
- Unicode全体はU+10FFFFまであり、UTF-16ではBMP外をサロゲートペアで表す

#### UTF-16 と UTF-8

- **Unicode**＝コードポイント（文字集合）／**UTF-16・UTF-8**＝実際のバイト列への変換**方式**
- UTF-16：16ビット符号単位、拡張部はサロゲート（Javaの内部表現）／UTF-8：**可変長**

**UTF-8 の符号化規則**

|バイト数|コードポイント範囲|ビットパターン|
|---|---|---|
|1バイト|U+0000 – U+007F|`0xxxxxxx`|
|2バイト|U+0080 – U+07FF|`110xxxxx 10xxxxxx`|
|3バイト|U+0800 – U+FFFF|`1110xxxx 10xxxxxx 10xxxxxx`|
|4バイト|U+10000 – U+10FFFF|`11110xxx 10xxxxxx 10xxxxxx 10xxxxxx`|

- **1バイト文字（U+0000–007F）は ASCII とまったく同じ**＝後方互換
- バイト長で先頭バイトのパターンが決まり（2バイト→`110`、3バイト→`1110`）、**2バイト目以降は必ず `10`** で始まる → 途中バイトと先頭を区別できる

#### 絵文字

- もとは日本の携帯電話文化から普及し、Unicodeへ収録された
- 絵文字にはBMP内・BMP外の両方があり、1コードポイントとは限らない
- 肌色修飾子、異体字セレクタ、ゼロ幅接合子などを組み合わせた列で1つの表示を作る場合がある

## Web技術

### Webとは何か

- **WWW（World Wide Web）** は1989年にCERNのティム・バーナーズ＝リーが発明した、ハイパーリンクで相互接続された情報空間
- 通信は **HTTP/HTTPS**（アプリケーション層）
- **Web ≠ インターネット**
- インターネットは下層（IP・TCP等）の基盤
- Webはその上で動く**1つのアプリケーション**にすぎない

### HTTPとハイパーテキスト

- **HTTP**はWWWの通信プロトコル
- ハイパーテキスト＝「参照付きの電子的文章」
- 文書記述には **HTML** を用いる
- HTTPはWeb以外でも使われる

### Webが革新的だった理由

- ハイパーリンクにより、**異なるサイト・メディア・人々をつなぐリンク構造**を提供
- サイト間リンクが導線を作り、広告収入モデルやソーシャルメディアを生んだ

### HTTPの歴史

|バージョン|時期|ポイント|
|---|---|---|
|HTTP/0.9|1991|最初期|
|HTTP/1.0|1991–1995 (RFC 1945)||
|HTTP/1.1|1996–1997 (RFC 2068)|長く主流|
|HTTP/2|2015、2022改訂 (RFC 9113)|バイナリフレーミングと多重化。元はGoogle SPDY|
|HTTP/3|2022 (RFC 9114)|HTTPの意味論を、UDPベースのQUIC上で転送|

### URL と URI

- **URL** は上位概念 **URI**の一例

### HTML

- Web文書の構造と意味を記述する**マークアップ言語**
- 現在はWHATWGの **HTML Living Standard** が継続的に更新されている
- W3CがHTML5を「無効な技術」にしたという意味ではなく、独立した版番号のスナップショットよりLiving Standardへ標準化の中心が移った

### HTTPリクエストメソッド

|メソッド|意味|
|---|---|
|**GET**|URLで指定したデータを要求（取得）|
|HEAD|GETと同じだがヘッダのみ取得|
|**POST**|データを送信（name, value の組）|
|PUT|指定ファイルを置き換える|
|DELETE|指定ファイルを削除|
|TRACE|リクエスト内容をそのまま返す（エコー）|
|OPTIONS|オプションの通知|
|CONNECT|HTTPトンネリング（proxy + SSL/TLS時など）|

### HTTPステータスコード

- 3桁の数字
- **百の位で大分類**
	- 2xx=成功
	- 3xx=リダイレクト,
	- 4xx=クライアント側エラー
	- 5xx=サーバ側エラー）

| コード | 名称                    | 説明                 |
| --- | --------------------- | ------------------ |
| 200 | OK                    | 成功                 |
| 206 | Partial Content       | 部分的なコンテンツ（途中から開始）  |
| 302 | Found                 | 一時的なリダイレクト         |
| 401 | Unauthorized          | 有効な認証資格情報がなく、認証が必要 |
| 403 | Forbidden             | サーバは要求を理解したが実行を拒否  |
| 404 | Not Found             | リソースが存在しない         |
| 500 | Internal Server Error | サーバ内部のエラー          |
| 503 | Service Unavailable   | 一時的に利用不可（高負荷など）    |

### WWWのアーキテクチャ

- 基本は**クライアント・サーバモデル**
- サーバは到達可能なIPさえあればどこにあってもよい

### 発展技術が必要になった背景

- **規模**：利用者・サービス・トラフィックが大幅に増え、単一サーバでは可用性と性能を維持できない
- **質**：静的→動的コンテンツ、広告収入モデル、一極集中化
- 対応技術は (1)アーキテクチャの進化 (2)分散技術 (3)高速化 の3本柱

### アーキテクチャの進化

- 単純なHTML・画像配信なら**二層**（クライアント・サーバ）で十分
- DB検索や動的生成には**三層アーキテクチャ**で処理を分散しスケーラビリティを上げる

| 層          | 担当            | 実装例                                               |
| ---------- | ------------- | ------------------------------------------------- |
| プレゼンテーション層 | データ表示（クライアント） | ブラウザ                                              |
| アプリケーション層  | データ加工         | Webサーバ Apache／アプリサーバ JavaEE, .NET, Rails, Node.js |
| データ層       | データアクセス       | DBサーバ MySQL, Oracle                               |

- クライアントがリクエスト → Webサーバがクエリ → DBサーバが検索結果 → Webサーバがデータ加工してHTML出力
- **動的ウェブコンテンツ**：サーバ側（アプリサーバ）とクライアント側（**JavaScript**）の両方で動作

### 分散技術

#### ローカルな分散

- 複数サーバのPCクラスタが単一サーバのように振る舞う
- 負荷分散に**ロードバランサ**や**DNSラウンドロビン**
- **リバースプロキシ**でアクセス頻度の高いリクエストをフロントでキャッシュ

#### グローバルな分散**

- 遅延、負荷、障害、契約などを考慮して配信拠点を選ぶ
- コンテンツの事前配置やキャッシュ、DNS応答、anycastなど複数の仕組みを組み合わせる

### 高速化

#### キャッシュ

- アクセスは偏るのでキャッシュが効く
- 制御は**HTTPの Cache-Control ヘッダ**などで行う
- 静的か動的かだけで決まるのではなく、応答内容と更新要件に応じてキャッシュ可否を指定する

#### プロトコル改良

- HTTP/1.1パイプラインは先行応答待ちによるHOLブロッキングがあり普及しなかった
- 複数TCP接続による並列化を経て、HTTP/2は1接続上で複数ストリームを多重化した
