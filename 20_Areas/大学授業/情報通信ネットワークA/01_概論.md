## 情報通信ネットワークA：概論

- 親ノート: [[情報通信ネットワークA]]

## ネットワークの基本概念（概論）

### コンセプト1：集中か自律分散か

- 膨大な数のコンピュータが相互通信するネットワークを、どのように設計するかが課題
- **ナイーブな解** 
	- すべての端末を直接つなぐ方法（メッシュ型）
	- しかし端末数 n に対して必要な回線数が **n² のオーダー**になり、1拠点から多数の場所へ回線を敷く必要が生じる
- **現実的な解** 
	- 中央に「スイッチ」を置き、端末とスイッチの間だけ回線を引く
	- スイッチが端末間の接続を動的に切り替える


|          | 集中システム                    | 自律分散システム                            |
| -------- | ------------------------- | ----------------------------------- |
| 定義       | 中央のシステムがスイッチ・端末を一元的に制御・管理 | 複数の管理主体がそれぞれの方針で動作し、共通プロトコルによって相互接続 |
| 具体例      | 公衆交換電話網                   | インターネット                             |
| 障害耐性     | △                         | ⚪︎                                  |
| 仕様変更の柔軟性 | ⚪︎                        | △                                   |

### コンセプト2：回線かパケットか

#### 回線交換

- 公衆交換電話網のために開発された古い方式（1870年頃〜）
- 通信開始前に、論理的な回路を**専有的に割り当てる**
- **コネクション指向型**

#### パケット交換

- 1960年代初頭に提案され、ARPANET（1969年運用開始）で採用
- データを「パケット」という小さな単位に細切れにし、**バケツリレー**で転送
- 事前に専有割り当てをしない → **ネットワーク資源を共有**
- パケット交換には、IPのような**データグラム型**と、事前に論理経路を設定する**仮想回線型**がある
- インターネットのIPは**コネクションレスかつベストエフォート**


|       | 回線交換                  | パケット交換             |
| ----- | --------------------- | ------------------ |
| 資源    | 帯域を予約し、予測可能な品質を設計しやすい | 共有→有効利用できる         |
| 到着順序  | 必ず送信順                 | 必ずしも送信順にならない       |
| 障害時   | 確率中の回線は影響を受ける         | 経路制御が収束すれば別経路へ迂回可  |
| 欠点    | 帯域の無駄が多い、集中管理のコスト     | 混雑、遅延の揺らぎ、品質保証できない |
| 適した用途 | 音声通信                  | データ通信              |


### コンセプト3：エンドツーエンド原理

#### エンドツーエンド原理（E2E）

- インターネットの設計原理
- 通信の正しさを最終的に確認するには、アプリケーションの要求を知るエンドポイントでの処理が必要である

#### E2E暗号

- 通信するエンドポイントだけが平文を読める状態を実現するには**E2E暗号が必要**
- これがあれば、途中の ISP や電話会社がデータを盗聴しても中身は読めない
- ただし宛先IP、通信量、タイミングなどのメタデータまですべて隠れるわけではない
- セキュリティ・プライバシーの実現に欠かせない技術

### コンセプト4：分業・モジュール化

#### モールス信号にみるレイヤー

- モールス信号は2つの層に分けられる
	- 上位層：**モールス符号**
	- 下位層：**物理層**
- モールス符号は物理的な媒体によらず使える「汎用的な通信方式」
- 出現頻度の高い文字に短い符号を割り当てている点も効率化の工夫
- このように**通信の機能を階層的に分割する**のがレイヤーの考え方

#### レイヤーを導入する利点

- 各層が独立した機能を持つ（**モジュール化**）→ 開発効率が飛躍的に向上
- 機能追加にシステム全体を作り直す必要がない
- トラブル時に層ごとに調査できる

#### OSI参照モデル

- ISO（国際標準化機構）が標準化した、通信機能を特徴づける抽象モデル
- 7層からなり、**下位層は上位層にサービスを提供**

|層|名称|役割|
|---|---|---|
|L7|アプリケーション層|異なる端末間のアプリケーション間通信を規定|
|L6|プレゼンテーション層|データを表現する文法や意味を規定|
|L5|セッション層|異なる端末上のプロセス間通信を規定|
|L4|トランスポート層|異なる端末間の通信チャンネルを規定|
|L3|ネットワーク層|アドレス、経路選択方法を規定|
|L2|データリンク層|同一リンク上のフレーム転送、媒体アクセス、誤り検出などを規定|
|L1|物理層|物理的な伝送路上でデータを伝送する方法を規定|

### コンセプト5：全世界共通のルール（プロトコル）

#### プロトコルの必要性

- ネットワークには様々なハードウェア・OS・ソフトウェアの端末が接続される
- これらが相互通信するには共通のルールが必要で、これが**プロトコル**
- 標準プロトコルを定めて実装することで、あらゆる端末がインターネット越しに通信できる

#### 標準化の歴史的背景

- 当初は各社が独自プロトコルで「囲い込み」をして独占的立場を築こうとした
- しかし互換性のなさが発展の阻害要因となり、標準化の必要性が生まれる
- **プロトコルは標準化し、その上で実現するサービスで差別化する**という戦略
- 標準化団体には **ISO、IEEE、IETF、W3C** などがある

#### レイヤーとプロトコルの関係

- **同一階層間**の規定 → **プロトコル**（端末Aの第n層と端末Bの第n層が通信）
- **上下階層間**の規定 → **インターフェース**

#### TCP/IP

- OSI参照モデルが抽象的な汎用モデル
- TCP/IP は**1974年に ARPANET 向けに開発**された、**具体的なプロトコルが存在する**レイヤーモデル
- 中核は TCP と IP の2つ


|           | OSI参照モデル                | TCP/IP                             |
| --------- | ----------------------- | ---------------------------------- |
| 起源        | ISOによって定められた国際標準        | ARPANET向けに開発された仕様及び実装があり、後から標準化された |
| 標準化機関     | ISO                     | IETF                               |
| 位置付け      | 参照モデルとして残ったが、実装は普及しなかった | デファクト・スタンダード                       |
| プロトコルとの関係 | プロトコルに非依存の参照モデル         | TCP/IPありきのモデル                      |

#### 層の対応

|OSI（7層）|TCP/IP（4層）|
|---|---|
|アプリケーション／プレゼンテーション／セッション|Application|
|トランスポート|Transport（TCP, UDP）|
|ネットワーク|Internet（IPv4, IPv6）|
|データリンク／物理|Link|

#### カプセル化

- データが上位層から下位層へ降りるとき、各層で**ヘッダ**が先頭に追加されていく
- アプリケーション層：`データ`
- トランスポート層：`TCPヘッダ + データ`
- IP層：`IPヘッダ + TCPヘッダ + データ`
- データリンク層：`ヘッダ + （上記すべて）`

### コンセプト6：暗闇のキャッチボール

- パケット通信の本質を表す比喩
- 送信側から見ると、投げたパケットが相手に届いたかどうかが**見えない**
- **Ackパケット**：確認応答（届いたよ、の返事）
- **シーケンス番号**：パケットの通し番号
- **タイムアウト**：時間切れの判定（一定時間Ackが来なければ再送）
- **データリンク層**と**トランスポート層**でこの考え方が使われる

### コンセプト7：失敗を前提とした世界

- 共有媒体上の信号衝突や無線干渉、ルータのバッファあふれなどによって、フレームやパケットは失われる可能性がある
- インターネットは、下位層で損失が起こりうることを前提に、必要な信頼性を上位層で補えるよう設計されている

#### データが損失するケース

- 無線で異なる端末が同時送信した
- 無線信号が途中で**減衰**した
- 共通バスで電気信号が**衝突**した
- 装置の処理容量を超えるパケットが入力され**廃棄**された
- ハードウェアの不具合

#### 損失への対策（誤り制御）

- **誤り検出 → 再送**
- **誤り訂正 → あらかじめ冗長性を持たせたデータを送る**
- 再送
- **データリンク層**と**トランスポート層**でこの考え方が使われる

### 全体を貫くつながり

- コンセプト1で「自律分散（インターネット）」を選び、コンセプト2で「パケット交換」を選んだ結果、**資源共有・ベストエフォート**になる
- ベストエフォートでは到達が保証されず、**パケットが失われる可能性がある**（コンセプト7）
- 失われても回復するために**Ack・シーケンス番号・タイムアウト・再送**（コンセプト6）が必要
- これらの賢い処理はネットワークではなく**エンド**が担う（コンセプト3 = E2E）
- 多様な端末をつなぐために**レイヤー化（4）とプロトコル標準化（5）**が必要
